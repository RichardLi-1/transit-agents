# Results, 2026-11-16

The first accuracy numbers for the agents, from one night on one laptop. A small open model
(Qwen3.5 4B, 4-bit) ran every agent role on the planner-reviewed eval cases (run A). A LoRA
adapter was then trained on run A's passing dev cases, and the adapter ran the same test
cases (run B). Run C, the base model without skills, was dropped to report sooner.

Headline, on the 24 scored test cases that both runs answered:

- Run A, base model with skills: **5 of 24** test cases passed. On dev: **14 of 36**.
- Run B, LoRA adapter with skills: **8 of 24** test cases passed.
- B minus A: **+3 cases (+12 points)**. B passed 6 cases A failed, and failed 3 that A
  passed. 6 against 3 is well within chance (exact McNemar p = 0.51), so this is no evidence
  that the adapter helps, or that it hurts.

In all, run A passed **19 of 60** scored cases. One run per case, so read every difference
here as within noise unless it's large. With 24 cases, one case is about 4 points.

## Setup

- **Model:** `mlx-community/Qwen3.5-4B-4bit`, Qwen3.5 4B quantised to 4 bits for MLX. It ran every
  role: the lead, the specialists and the eval reader. Run B used the same model with the
  adapter below.
- **Server:** mlx-lm 0.32.2 (MLX 0.32.4), `mlx_lm server` on port 8090, through the repo's
  OpenAI-compatible client ([openai_compat.py](../agents/openai_compat.py)). The server was started with
  `--temp 0.7 --top-p 0.8 --top-k 20`,
  `--chat-template-args '{"enable_thinking":false}'`, `--prompt-cache-size 4` and
  `--prompt-cache-bytes 1GB`. Run B added `--adapter-path`. The agents named the model
  `default_model`, the server's name for whatever `--model` and `--adapter-path` it was
  started with. Asking for the model by its repo name would have loaded it again without
  the adapter.
- **Request settings:** `MODEL_EXTRA={"max_tokens": 4096}`, which caps each reply at 4,096
  tokens, below the repo's 16,384, so a looping reply costs minutes, not a quarter of an hour.
  Everything else was the repo's defaults: 30 model calls an agent, 60 a run.
- **Reader:** the same model, so rule 6 ("keep the judge separate from the agent") is broken.
  The laptop had no memory for a second model. The reader only fills the answer's fields:
  refusals, abstentions and flags are scored from the case's log, and a script reads the
  citations.
- **Machine:** a MacBook Pro with an Apple M4 and 16 GB of memory, on macOS 15.5. Only one
  model process ran at a time: the server or training, never both. No Gemini model and no
  Gemini key were used.
- **Code:** branch `eval/overnight`. Each run used the runner
  (`python agents/main.py eval --limit 100 --case ...`, as `npm run agent:eval` does) with
  `EVAL_MODEL_LOGS=1` and `EVAL_PORTS=4326-4330`. Scores come from
  [score-run.ts](../evals/score-run.ts). Prompts, skills and the scorer didn't change between
  runs A and B.

## Cases

The planner-reviewed cases are the 66 in [cases.jsonl](../evals/cases.jsonl) without
`"review": "planner"`: 38 dev, 27 test and 1 future. The future case (`monitor-001`) was left
out. The runner skipped 3 more because the seeded service lacks their source:
`find-009` and `reconcile-002` (test; `ttc-standards-deck-2025`) and `find-010` (dev;
`ttc-standards-note-2025`). So 62 cases ran: 25 test and 37 dev. One test case and one dev
case are scored by rubric, not by script, and no rubric scoring was done, so **60 cases were
scored: 24 test and 36 dev**.

What failed most:

- **Flags: 0 of 9.** A flag is scored from the log: it needs a question for a planner,
  recorded by `ask_planner`. In 8 of the 9 flag cases there was none. In the ninth,
  `review-001`, the question was recorded, but the answer still recommended an outcome (read
  as reject, where the gold is defer). Across all of run A, `ask_planner` was called 4 times
  in 3 cases, and the service recorded only `review-001`'s question.
- **Checks: 2 of 12.** On a proposal check, the model often gave no decision, or called a
  test not assessed.
- **Abstaining when it should answer.** On 5 spatial cases, 2 calculations and 1 check, the
  model said it couldn't answer, where the gold has an answer.
- **Two errors** in run A, both dev: the reader once echoed the JSON schema in place of an answer
  (`define-004`), and `spatial-003` used the run's 60 model calls (28 minutes) without an answer.
  Both are scored as failures. Run B had no errors.

## Fine-tuning

- **Data:** run A's passing dev cases only, never a test case. Run A's test answers and
  scores weren't read until run B was done, apart from the count the runner prints at the
  end (5 of 24). 14 dev cases passed. From their
  model logs, [extract.py](../agents/sft/extract.py) rebuilt each agent's whole conversation,
  the lead's and its specialists', without the reader's call: 15 conversations (14 leads and
  1 safety-audit specialist), 166,516 tokens, of which 10,496 are the model's own turns.
- **Kept:** [train.py](../agents/sft/train.py) drops a conversation longer than `--max-tokens`
  after its shared opening (the system message and tool declarations). At 6,000, which
  memory allowed, **9 of the 15 conversations were kept**, all leads, from 9 cases: `define-003`,
  `find-001`, `find-004`, `find-005`, `find-006`, `stop-002`, `stop-006`, `stop-007` and
  `trace-001`. Each epoch was 33,612 tokens after the openings, with 2,622 of them trained on
  (the assistant's turns). The 6 long ones, from `check-001`, `define-001`, `define-002`,
  `define-005` and `spatial-008` (lead and specialist), were dropped. So the adapter saw
  only short lookups: no check, spatial or multi-specialist case.
- **Settings:** LoRA on the last 4 of 32 layers, rank 8, scale 20, learning rate 1e-4
  (3 warm-up steps, then cosine), 2 epochs = 18 steps, one conversation a step, seed 0:
  2,029,056 trainable parameters.
- **Time and loss:** 10.2 minutes, 67,224 tokens. Mean training loss 0.351 in the first epoch
  and 0.126 in the second (first step 0.810, last 0.358). No validation split: there were too few
  conversations. A training loss this low on 9 conversations is memorising, not a sign of
  generalising. Peak memory was 17.9 GB, more than the laptop has, so training swapped.

and reader. Only the adapter differs.

| **All** | **5/24 (21%)** | **8/24 (33%)** |
| answer | 5/20 | 7/20 |
| flag | 0/4 | 1/4 |
| ttc-standards | 2/16 | 5/16 |
| gis-analyst | 3/5 | 2/5 |
| consultation | 0/3 | 1/3 |
| calculate | 1/5 | 3/5 |

| consultation (capability) | 0/2 | 1/2 |
| find | 0/2 | 1/2 |
| spatial | 3/5 | 2/5 |
| stop | 0/1 | 0/1 |

Case by case: both passed 2, both failed 13. B alone passed 6: `calc-005`, `calc-006`,
`consult-002`, `find-011`, `review-001` and `spatial-007`. A alone passed 3: `check-004`,
`spatial-004` and `spatial-010`. An exact McNemar test on 6 against 3 gives p = 0.51.

So the adapter's +3 cases is no evidence either way. Some of the swaps look like sampling
noise: `calc-005` failed in A on 33.5 against 33.6, and B lost two spatial cases by
abstaining, where A answered. The 9 training conversations were all short lookups, and none
were spatial or check cases.

Run B also worked longer: 13.9 model calls a case against 9.5, and nearly twice the input
tokens. Part of that is one loop: in `review-003`, B's lead called `ask_planner` 20 times with
the same over-long detail, and the service refused each one (its limit is 600 characters), so
no question was recorded and the case failed. Whether the extra work is the adapter's or
chance, one run can't tell.

## Departures from the plan

- **Run C (base model, no skills) wasn't run.** It was dropped so results could be
  reported sooner. So this report can't say what the skills add.
- **The 21:00 stop for run A failed.** A script was to stop run A at 21:00. It matched two
  processes and its `kill` failed, so run A's dev half ran to the end at 22:50. That cost about
  two hours and changed no result: run A then covered every runnable reviewed case.
- **Test cases first.** Run A ran its 25 test cases first (`20261115T235557Z`) and then its 37
  dev cases (`20261116T004811Z`), as two run files, so a stop could never lose test cases.
- **A JSON fix for the reader, before any run.** mlx-lm's server ignores `response_format`,
  so the reader answered in prose and every case failed to parse. Commit `e2c5502` makes
  [openai_compat.py](../agents/openai_compat.py) ask for JSON in words too, with the schema, and keep
  the reply's first JSON value. It changes only requests that ask for JSON, which in an eval
  is the reader's call alone, and it was in place for runs A and B alike. Even so, the reader
  once echoed the schema in place of an answer (`define-004`, scored as a failure).
- **Per-case model logs.** Commit `3022d9f` adds `EVAL_MODEL_LOGS` to the runner, so each
  case's raw model calls are kept, the reader's apart, for extracting conversations.
- **Short training, on part of the data.** Training was kept to about 10 minutes and 6,000
  tokens a conversation, as asked, for memory and time. That dropped 6 of 15 conversations.
- **The agents' Python** was the main checkout's virtual environment, linked into the worktree
  (not committed). Nothing in the main checkout changed.

## Limitations

- **One run per case.** The model samples at temperature 0.7, so a case can pass in one run and fail in the
  next. The repo asks for 3 runs or more. Nothing here measures that spread.
- **24 test cases.** One case is about 4 points, and a confidence interval on any pass rate here spans
  tens of points.
- **The reader is the agents' own model**, against rule 6, and a 4B one. Its field readings
  decide answer cases' values, decisions and test results. It failed outright once in
  run A (`define-004`). Its readings weren't checked by hand.
- **The training set is tiny:** 9 conversations from 9 dev cases, all short lookups. Twenty minutes
  of training on that can't be expected to move the test score much, and can't show what
  fine-tuning on more data would do.
- **The committed test split is public.** Its cases and answers are in a public repo, so a
  model may have seen them. Report these as scores on public cases.
- **Rubric cases weren't scored.** Of the cases that ran, 1 test and 1 dev case are rubric cases.
- **Settings chosen here, not tuned:** sampling, the 4,096-token cap and thinking off were
  chosen before run A and held for run B, but other choices could score differently.

## Reproduce

```sh
# serve (run B adds --adapter-path <adapter>)
mlx_lm server --model mlx-community/Qwen3.5-4B-4bit --port 8090 --temp 0.7 --top-p 0.8 --top-k 20 \
  --chat-template-args '{"enable_thinking":false}' --prompt-cache-size 4 --prompt-cache-bytes 1GB
# run (without GEMINI_API_KEY)
MODEL_BASE_URL=http://127.0.0.1:8090/v1 LEAD_MODEL=default_model SPECIALIST_MODEL=default_model \
  READER_MODEL=default_model MODEL_EXTRA='{"max_tokens": 4096}' EVAL_MODEL_LOGS=1 \
  agents/.venv/bin/python agents/main.py eval --limit 100 --case <id> ...
node evals/score-run.ts --json evals/runs/<run>.jsonl
# train, in the MLX venv, after stopping the server
python agents/sft/extract.py --run evals/runs/<run A dev>.jsonl --scores <its --json scores> --out train.jsonl
python agents/sft/train.py --data train.jsonl --out adapter --layers 4 --rank 8 --scale 20 --lr 1e-4 \
  --warmup 3 --steps 18 --max-tokens 6000 --seed 0
```

The run files (`evals/runs/`, not committed) are `20261115T235557Z` (A, test),
`20261116T004811Z` (A, dev) and `20261116T040228Z` (B, test). Each case's log and model calls are in the folder
of the same name.
